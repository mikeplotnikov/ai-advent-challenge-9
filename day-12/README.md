# День 12 — персонализация ассистента

Задание: «Добавьте персонализацию поверх модели памяти: создайте профиль пользователя;
опишите предпочтения (стиль, формат, ограничения); подключите профиль к каждому запросу.
Проверьте: ответы для разных профилей; что ассистент учитывает автоматически.»

Реализация — в том же агенте недели 2 (`internal/agent/profile.go`), интерфейс — тот же CLI
`day-06` под флагом `-layers`. Здесь, в `day-12/`, лежат описание, драйвер замера, сырые
строки прогона `profiles.jsonl` и отчёт `RESULTS.md`, собранный из них.

## Профиль — это не память

Ведущий провёл эту границу сам, когда участник предложил перенести свою персонализацию из
краткосрочной памяти в долговременную: **«Нет. Память это память»** [чат #2898], **«А профиль
это нюансы конкретного пользователя»** [#2899]. Поэтому профиль — отдельная сущность со своими
файлами, своим блоком в промпте и своим сроком жизни, а долговременный слой дня 11 оставил
себе только то, что действительно память: решения и знания.

| | Память (день 11) | Профиль (день 12) |
|---|---|---|
| Что хранит | что было: диалог, данные задачи, решения, знания | каким быть: как отвечать, чего держаться, кто спрашивает |
| Кто наполняет | пользователь по ходу работы | пользователь настраивает заранее, в т.ч. интервью |
| Где лежит | `.memory/<user>/sessions\|tasks\|long-term.json` | `.memory/<user>/profiles/<name>.json` |
| Как попадает в запрос | `[LONG_TERM_MEMORY]` и `[WORKING_MEMORY]` | `[PROFILE]` в самом начале system |
| Сколько штук | один набор слоёв на пользователя | несколько профилей + роутер |

Раздел `profile`, который день 11 держал внутри долговременного слоя, переехал сюда.
`long-term.json` версии 1 мигрирует при первом чтении: записи уезжают в профиль `default`,
файл слоя переписывается в версию 2. Миграция идемпотентна и никогда не затирает
предпочтение, выставленное после неё. Команда дня 11 `/remember profile КЛЮЧ = ЗНАЧЕНИЕ`
работает и печатает, куда именно ушла запись.

## Три блока

Схема — со слайда 11 урока 3: **STYLE** (как отвечать), **CONSTRAINTS** (чего держаться),
**CONTEXT** (кто спрашивает).

```json
{
  "version": 1, "user": "михаил", "name": "senior", "pipeline": "direct",
  "style":       [{"key": "detail",  "value": "Отвечай коротко, без вводных абзацев"}],
  "constraints": [{"key": "stack",   "value": "Только Kotlin. Не предлагай Java и Spring"}],
  "context":     [{"key": "project", "value": "Мобильный банк, команда 4, дедлайн 2 недели"}]
}
```

Записи ограничены на входе так же, как записи слоёв: до 32 в блоке, ключ — буквы, цифры,
`_ - .` до 64 символов, значение — одна строка до 500. Одна строка на запись гарантирует, что
значение не подделает соседнюю запись или тег блока.

## Как профиль попадает в запрос

```text
system:  базовый промпт
         [PROFILE] style.… constraints.… context.…
         [LONG_TERM_MEMORY] decision.… knowledge.…
         (summary дня 9 и facts дня 10, если их ведёт выбранная стратегия)
history: краткосрочный слой
user:    [WORKING_MEMORY] … [PLAN] … [USER_MESSAGE] новый вопрос
```

- **Профиль стоит первым.** Порядок сборки — ведущего: «общий prompt, потом данные
  персонализации, потом summary с предыдущего шага» (урок 3, 09:12). Он же выгоден кэшу:
  профиль меняется реже всего, а провайдер кэширует начало запроса.
- **Пустой или выключенный профиль не добавляет ни байта:** запрос побайтно такой же, как в
  днях 6–11 (тест).
- **Флаг `-inject` выбирает, что уходит:** `short,working,long` — слои дня 11,
  `profile` (или `style`, `constraints`, `context` по отдельности) — блоки профиля. Это ручная
  абляция и одновременно совет урока: «где-то не важен профиль, вы там это пропускаете»
  (слайд 29, антипаттерн 01).

## Несколько профилей и роутер

Ведущий на вопрос, может ли у одного пользователя быть несколько профилей: «В целом да, его
можно побить на файлы, сделать общий профиль-роутер и потом выбирать уже конкретный» [#2903].
Роутер — детерминированная таблица подстрок в `profiles/_router.json`: первое совпадение по
порядку, иначе `default`. Модель в выборе профиля не участвует, поэтому один и тот же вопрос
всегда попадает в один и тот же профиль. По умолчанию роутер выключен: профиль держится на
сессию, и начало запроса не меняется от хода к ходу.

## Конвейер профиля

Ведущий в тот же день поднял планку: «Профиль = пайплайн из скиллов… то есть оркестрация
скиллов» [#2913–2915]. В тексте задания этого нет, а вопрос участника, обязательна ли
настраиваемая последовательность [#2921], к концу дня остался без ответа. Поэтому сделан
минимальный мостик: поле `pipeline` с двумя значениями.

- `direct` — один вызов, поведение дней 6–11.
- `plan-answer` — два последовательных вызова: сначала короткий план, затем ответ с этим
  планом перед вопросом. План живёт один ход и в диалог не сохраняется.

Неудача шага плана проваливает ход целиком: ответить без плана значило бы молча подменить
конвейер, который выбрал пользователь.

## Интервью при инициализации

Урок советует собирать профиль интервью: «если вам пишет новый ID… проведи с ним базовое
интервью» (слайд 11). `/profile init` задаёт семь фиксированных вопросов и раскладывает
ответы по трём блокам. **Ни одного вызова модели:** вопросы — константы, пустой ответ
пропускается. Детерминированное интервью бесплатно и воспроизводится тестом.

## Диалог руками

```bash
go run ./day-06 -layers -user михаил -profile senior
> /profile init
> /profile set constraints stack = Только Kotlin, без Java и Spring
> /profile pipeline plan-answer
> /profile
> Объясни, что такое dependency injection.
> /profile use analyst
> Объясни, что такое dependency injection.
```

## Проверка

```bash
go run ./day-12 -pilot -out /tmp/pilot.jsonl                 # 5 живых вызовов
go run ./day-12 -out day-12/profiles.jsonl                   # полный прогон
go run ./day-12 -report day-12/profiles.jsonl > day-12/RESULTS.md
go run ./day-12 -dump > ../uchebnik-ai-advent/challeng/test/day12-definitions.json
```

Все числа — в `RESULTS.md`, и ни одно из них не вписано руками: отчёт пересобирается из JSONL
и сравнивается побайтно тестом. Прогон состоит из четырёх частей:

- **E0** — слайд 16 вживую: один вопрос, четыре профиля, ответы целиком.
- **A — соблюдение предпочтений.** Один вопрос во всех руках, ответ оценивается несколькими
  двоичными критериями. N = 30 (у контрольной пробы 20).
- **C — конфликт.** Вопрос прямо просит то, что профиль запрещает. Это проверка тезиса
  слайда 29 «текстовое правило — просьба, не закон» на нашей модели.
- **D — конвейер и цена.** `direct` против `plan-answer`; вес профиля и доля кэша.

Что стоит прочитать в `RESULTS.md` помимо главных таблиц:

- **Отрицательный контроль сработал:** на арифметике ни одна рука не отличается от `none`
  (p = 1.000 во всех трёх сравнениях). Прибор умеет сказать «различий нет» — значит его
  «различие показано» в остальных строках что-то стоит.
- **Разрешение и запрет работают по-разному.** «Приводи примеры кода» неотличимо от базовой
  руки: модель и без профиля даёт код в 30/30. А запрет «не приводи примеров кода» уводит
  долю в 0/30. Предпочтение, совпадающее с поведением по умолчанию, измерить нельзя —
  и заплатить за него токенами всё равно придётся.
- **`context` — самый слабый блок.** Обстоятельства профиля (дедлайн, размер команды)
  всплывают в ответе заметно реже, чем соблюдаются стиль и стек. Проба маркерная: она видит
  упоминание, а не учёт.
- **Обрыв по потолку раскрыт отдельной колонкой.** У руки `junior` обрезаны все 60 ответов на
  оба содержательных вопроса (на арифметику — ни одного): «отвечай подробно» упирается в
  `max_tokens`. Критерии на присутствие в оборванной клетке могли не увидеть хвост; критерии
  на отсутствие и на начало ответа от обрыва не страдают.
