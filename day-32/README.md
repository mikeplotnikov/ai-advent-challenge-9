# День 32 — автоматическое AI-ревью PR

На каждый pull request запускается workflow `.github/workflows/day-32-review.yml`. Ассистент:

1. **Получает diff и изменённые файлы** — `git diff base...head` (то, что GitHub показывает во вкладке
   «Files changed»), у каждой строки номер в новой версии файла, плюс изменённые файлы целиком.
2. **Ищет контекст в RAG — документация + код.** Документация: `README.md` и `docs/` (чанкинг по заголовкам
   из `internal/docrag`), в том числе правила ревью `docs/review-guide.md` — они запрашиваются на каждом ревью.
   Код: Go-файлы `internal/` и затронутых пакетов, по фрагменту на объявление верхнего уровня.
   Эмбеддинги — `bge-m3` в локальной Ollama, с кэшем между запусками: пересчитывается только изменившееся.
3. **Пишет ревью** — DeepSeek по REST, ответ в JSON (`response_format`), три раздела: потенциальные баги,
   архитектурные проблемы, рекомендации. У каждого пункта `файл:строка` и источники (`diff`, `D2`, `C5`).
4. **Публикует комментарий в PR**; при новом пуше тот же комментарий обновляется.

```
PR opened / pushed ─► runner (Mac) ─► git diff + файлы ─► RAG: docs + code (bge-m3) ─► DeepSeek ─► проверка ответа ─► комментарий в PR
```

## Надёжность (урок 7: error handling, retry, fallback, человек в цепи)

| Сбой | Что происходит |
|---|---|
| DeepSeek: сеть, 429, 5xx | до 3 попыток с паузами 2 и 5 с; 4xx кроме 429 не повторяется |
| Ответ не по схеме: файл не из PR, строки нет в файле, ссылка на источник, которого модели не давали | один повторный запрос со списком ошибок; что не исправлено — отбрасывается и перечисляется в комментарии |
| Ollama недоступна | поиск по словам (TF-IDF) вместо эмбеддингов, в комментарии пометка «Деградация» |
| Ревью не получилось совсем | комментарий «Ревью не выполнено: причина» и красный job — человеку два сигнала |
| Большой PR | diff и файлы режутся по лимиту, пропущенное перечисляется в комментарии |

Ревью не блокирует мерж: решение за человеком. Метрики каждого прогона — время по этапам, токены,
цена (`llm.CostAt`), сколько фрагментов взято из кэша — в подвале комментария и в сводке job.
Полезность — реакции 👍 / 👎 на комментарий.

## Раннер

Job идёт на self-hosted runner — Mac владельца, где уже стоят Ollama и `bge-m3`. Раннер включается
только на время работы:

```bash
ollama serve &              # если ещё не запущена
./day-32/runner.sh          # регистрирует раннер, включает DAY32_REVIEW; Ctrl-C — снимает всё обратно
```

Публичному репозиторию self-hosted runner опасен: PR может выполнить на машине чужой код. Единственная
настоящая защита — политика репозитория, которую `runner.sh` ставит на время работы: запуск из PR любого
внешнего участника ждёт одобрения владельца. **Пока раннер включён, такие запуски не одобрять.** Проверки
в самом workflow (только PR из этого репозитория, только при `DAY32_REVIEW` = `on`) PR может переписать —
они лишь не дают job висеть в очереди без раннера. На выходе (Ctrl-C, `kill`, закрытое окно) скрипт
снимает раннер с регистрации, выключает переменную, возвращает прежнюю политику и печатает итог.

Ключ DeepSeek в CI — секрет репозитория `DEEPSEEK_API_KEY_DAY18`, передаётся как `DEEPSEEK_API_KEY_DAY32`.

## Локальный запуск

```bash
go run ./day-32 -base origin/main -head HEAD           # ревью в stdout, без публикации
./day-32/eval/run.sh                                   # эталонные PR → day-32/eval/results/
go test ./day-32
```

Результаты прогонов — `RESULTS.md`.
