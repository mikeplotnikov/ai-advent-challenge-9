# День 11 — модель памяти агента

Задание: «Опишите и реализуйте модель памяти для агента. Разделите информацию минимум на
3 типа: краткосрочная (текущий диалог), рабочая (данные текущей задачи), долговременная
(профиль, решения, знания). Сделайте так, чтобы разные типы памяти хранились отдельно;
вы явно выбирали, что и куда сохраняется. Проверьте: какие данные попадают в каждый
слой; как это влияет на ответы агента.»

Реализация — в том же агенте недели 2 (`internal/agent/layers.go`), интерфейс — тот же
CLI `day-06` под флагом `-layers`. Здесь, в `day-11/`, лежат описание, драйвер замера,
сырые строки прогона `layers.jsonl` и отчёт `RESULTS.md`, собранный из них.

## Три слоя

| Слой | Что хранит | Где лежит | Сколько живёт | Кто пишет | Как попадает в запрос |
|---|---|---|---|---|---|
| краткосрочный | текущий диалог: пары вопрос–ответ | `.memory/<user>/sessions/<session>.json` — снимок беседы дней 7–10 | до `/reset` или новой сессии | агент, после каждого удачного хода | история сообщений между system и новым вопросом |
| рабочий | данные активной задачи, ключ = значение | `.memory/<user>/tasks/<task>.json` | до `/task done` | только команда `/remember task …` | блок `[WORKING_MEMORY]` перед новым вопросом |
| долговременный | профиль, решения, знания пользователя | `.memory/<user>/long-term.json` | пока запись не удалена `/drop` | только команды `/remember profile …`, `decision …`, `knowledge …` | блок `[LONG_TERM_MEMORY]` в system сразу после базового промпта |

Все три слоя — разные файлы с разным сроком жизни. `/reset` очищает только
краткосрочный слой, `/task done` удаляет только файл задачи, а долговременный файл
общий для всех сессий и задач пользователя.

## Явный выбор «что и куда»

Куда попадает запись, решает таблица в коде (`MemoryTarget.Layer`), а не модель:

| Команда | Слой |
|---|---|
| `/remember task КЛЮЧ = ЗНАЧЕНИЕ` | рабочий, только при активной задаче |
| `/remember profile КЛЮЧ = ЗНАЧЕНИЕ` | долговременный, раздел profile |
| `/remember decision КЛЮЧ = ЗНАЧЕНИЕ` | долговременный, раздел decisions |
| `/remember knowledge КЛЮЧ = ЗНАЧЕНИЕ` | долговременный, раздел knowledge |

- **Без активной задачи запись в `task` отклоняется** и никуда больше не уходит.
- **Модель в рабочий и долговременный слои не пишет:** её ответы остаются только в
  диалоге. Это закреплено тестом, в котором модель отвечает текстом `/remember …`, а
  файлы слоёв не меняются.
- **Ведущий разрешил сортировать память и вручную, и отдельным агентом** [чат #2800].
  Команды выбраны потому, что они детерминированы и не добавляют платного вызова на
  каждый ход.

Записи ограничены на входе: до 32 в разделе, ключ — буквы, цифры, `_ - .` до 64
символов, значение — одна строка до 500 символов. Одна строка на запись гарантирует,
что значение не подделает соседнюю запись или тег блока.

## Как слои собираются в запрос

```text
system:  базовый промпт
         [LONG_TERM_MEMORY] profile.… decision.… knowledge.…
         (summary дня 9 и facts дня 10, если их ведёт выбранная стратегия)
history: краткосрочный слой
user:    [WORKING_MEMORY] task: … ключ: значение
         [USER_MESSAGE] новый вопрос
```

- **Сначала то, что меняется реже:** провайдер кэширует начало запроса, поэтому
  долговременный блок стоит выше summary и facts.
- **Рабочий блок едет в хвосте** и в историю не сохраняется: в стек пишется сырой вопрос.
- **Пустой слой не добавляет ни байта:** при пустых слоях запрос побайтно такой же, как в
  днях 6–10 (тест).

Флаг `-inject short,working,long` выбирает, какие слои уходят в запрос. Выключенный
слой продолжает храниться — это ручная абляция.

## Совместимость с неделей 2

Краткосрочный слой работает под любой стратегией недели 2: полным диалогом, sliding,
summary (`-keep-last`), facts и branching. Рабочий и долговременный слои лежат вне
снимка беседы. Тест на каждую стратегию сверяет sha256 их файлов до и после ходов,
веток, сжатия и `/reset`.

## Проверка

```bash
go run ./day-11 -pilot -out /tmp/pilot.jsonl          # 5 живых вызовов
go run ./day-11 -out day-11/layers.jsonl               # полный прогон
go run ./day-11 -report day-11/layers.jsonl > day-11/RESULTS.md
go run ./day-11 -dump > ../uchebnik-ai-advent/challeng/test/day11-definitions.json
```

Прогон состоит из трёх частей, все числа — в `RESULTS.md`:

- **E0** — живой сценарий на реальных файлах. После записи, `/reset`, перезапуска, новой
  сессии и завершения задачи файлы трёх слоёв сканируются на маркеры, и результат
  сверяется с ожиданием.
- **A — вспоминание.** Одна и та же фикстура, меняется только набор слоёв в запросе.
  Коды в фикстуре непрозрачные, их нельзя угадать. Перед каждым вызовом проверяется, что
  маркеры выключенных слоёв не попали в отправленные байты; если хоть один попал, отчёт
  отказывается строиться.
- **B — поведение.** Долговременный профиль с правилом ответа и правилом стека сравнивается
  с руками без профиля: точный тест Фишера, поправка Холма.

Что стоит прочитать в `RESULTS.md` помимо главных таблиц:

- **Таблица «Что модель вернула в непрошедших ответах».** В руке `no-short` у модели нет
  диалога, но есть рабочий слой. На вопрос о номере тикета она ответила не `null`, а
  идентификатором из рабочего слоя. Доступный слой подтолкнул модель к неверному ответу
  там, где без слоёв вообще она честно отвечала `null`.
- **Контрольная проба (арифметика) иногда возвращает `null`** во всех руках. Системный
  промпт замера требует `null` для значений, которых нет в данных, и модель изредка
  относит к ним и арифметику. Это свойство промпта, а не слоёв.
